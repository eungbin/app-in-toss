**카테고리 — 비게임은 3단이고 중분류는 복수 선택이다**

콘솔은 비게임 앱의 카테고리를 **대분류 → 중분류 → 소분류** 로 받는다.
- **대분류는 '생활' 하나뿐이다**(2026-09-08 콘솔 확인). 비게임은 여기서 고를 게 없다.
  fx-replay 문서에 '라이프'로 적힌 것과 같은 항목으로 보인다. **실제 결정은 중분류에서 난다.**
- **중분류는 여러 개 고를 수 있다.** 단 같은 중분류를 두 번 고를 수는 없다.
- **소분류는 일부 중분류에만** 있고 중분류마다 항목이 달라서 목록화하지 않는다. 콘솔에서 보고 고른다.
- **중분류·소분류 목록은 개발자 문서에 없다.** 콘솔의 카테고리 선택 UI에서만 볼 수 있다.
  그래서 이 표에 값을 미리 못 박지 않고 선택 기준만 적는다.

**중분류 15개** (2026-09-08 콘솔 확인): 음식 · 교육 · 건강 · 교통 · 공공 · 소셜 · **편의** ·
쇼핑 · AI · 비즈니스 · 콘텐츠 · 여행 · 일상 · **정보** · 재테크

net-pay 판단

| 중분류 | 판단 |
|---|---|
| **편의** | **1순위.** 생활 편의 도구 자리. 계산기가 가장 자연스럽다 |
| **정보** | **2순위.** 공개된 세액표·요율로 계산해 알려주는 성격과 맞다 |
| 비즈니스 | 급여·퇴직금이 근로 관계라 후보이나 사업자·업무용 도구로 오해될 수 있다 |
| 일상 | 가능하나 범위가 넓어 발견성이 떨어진다 |
| 재테크 | **피한다.** 아래 |

**재테크를 피하는 이유와 트레이드오프**
발견성만 보면 재테크가 유리하다. 실수령액을 찾는 사람이 거기를 본다.
그러나 오픈 정책이 "대출·보험·카드·증권 등 금융 상품 관련 서비스"를 금지하는데
카테고리가 재테크면 심사자가 그 렌즈로 볼 가능성이 커진다. 이 앱은 금융 상품을
다루지 않는데도 설명할 일이 생긴다. fx-replay 도 같은 이유로 피했고 PRD 원칙 A2 가
그 판단이다. 발견성을 우선하려면 사전 상담으로 먼저 확인한다.

고른 값은 **채널톡 사전 상담 메시지(2장)와 같게** 적는다.

> **실제 고른 값 (2026-09-08)**: 비게임 · 생활 > 편의 > 도구

**주의 — 딥링크 식별자**

협상 카드의 링크 공유는 `intoss://net-pay/r?...` 를 만든다. `net-pay` 는
`apps-in-toss.config.ts` 의 `appName` 이고, SDK 문서에는 `intoss://` 뒤에 오는 값이
무엇인지 명시가 없다. 콘솔 등록 후 실기기에서 **링크를 눌러 앱이 열리는지** 반드시 확인한다.
열리지 않으면 콘솔이 쓰는 식별자로 `appName` 과 `src/engine/deeplink.ts` 의 `APP_NAME` 을 맞춘다.
링크 공유가 유일한 신규 유입 수단이라 여기서 막히면 손해가 크다.

### 1-2. 상세 설명 (콘솔 "상세 설명" 필드)

콘솔 가이드가 요구하는 **"서비스 접속 → 행동 → 결과"** 흐름으로 작성했다.
**500자 이내**여야 한다(콘솔 제한, 2026-09-08 확인 — 줄바꿈·공백도 센다).
아래는 **475자**다. 고치면 길이를 다시 센다.

> 국세청이 공개한 근로소득 간이세액표와 4대 사회보험 요율로 월급 실수령액을 계산하는 도구입니다.
>
> 앱에 들어오면 "세후로 월 얼마를 받고 싶은지" 묻는 입력창이 나옵니다. 금액을 넣으면 그 돈을 받기 위한 연봉이 바로 계산되고, 국민연금·건강보험·장기요양·고용보험·소득세·지방소득세가 항목별로 얼마씩 빠지는지 함께 보여 줍니다. 반대로 연봉을 넣어 월 실수령액을 볼 수도 있습니다.
>
> 같은 연봉이 몇 년 전이었다면 실수령이 얼마였는지 연도별로 비교하고, 결과를 카드 한 장으로 만들어 저장하거나 공유할 수 있습니다. 퇴직금과 미사용 연차수당 계산기도 들어 있습니다.
>
> 모든 결과는 공개된 세액표와 요율에 따른 참고용 계산이며 화면마다 적용 기준일을 함께 표시합니다. 금융 상품을 소개·연결하지 않고, 연봉이나 이직을 권하지 않습니다. 입력 금액은 서버로 보내지 않고 기기 안에서만 계산합니다. 사용자 간 경쟁, 현금성 보상, 확률형 요소가 없습니다.

첫 판은 513자로 13자를 넘겼다. 줄인 것은 표현뿐이고 심사에서 필요한 진술은 다 남겼다 —
참고용 계산·기준일 표시, 금융 상품 소개·연결 없음, 연봉·이직 권유 없음, 서버 미전송,
경쟁·현금성 보상·확률형 요소 없음.

### 1-4. 앱 검색 키워드

토스 앱 **전체메뉴 → 돋보기 검색**에 쓰이는 키워드다. 사용자가 어떤 말로 검색할지 예측해서 적는다.

**규칙** (2026-09-08 확인)
- **앱 이름은 기본으로 포함된다.** "세후로 말해줘", "NetPay" 를 키워드로 넣어 칸을 낭비하지 않는다.
- **미니앱과 관련 없는 키워드는 쓸 수 없다.** 검수에서 걸린다.
- **10개까지 넣는다.** 개발자 문서에는 개수가 없다. 10개를 상한으로 잡고 우선순위를 매겨 둔다.
  콘솔이 더 받아 주면 아래 대기 후보에서 이어 넣는다.
- 경쟁 서비스 이름(사람인·잡코리아 등)은 넣지 않는다. 오인 유도로 반려 사유가 될 수 있다.
- 카테고리에서 재테크를 피한 것과 같은 이유로 **재테크·투자·자산관리 류는 넣지 않는다.**

| 3 | 월급계산기 | 연봉계산기와 다른 검색 습관 |

### 1-5. 출시 노트 (검토 요청 시)

**`memo` 와 `releaseNote` 는 다른 필드다.** 콘솔 배포 조회에 둘이 따로 나온다.

| 필드 | 어디서 | 무엇 |
|---|---|---|
| `memo` | `ait deploy -m "…"` (1000자) | 배포 이력 메모. 내가 어느 번들인지 알아보기 위한 것 |
| `releaseNote` | **콘솔 검토 요청 화면** | 심사 담당자가 읽는 글. CLI 로는 넣을 수 없다 |

출시 번들의 deploy 메모(안): `v1.0.0 출시 번들 — 실 광고 ID. 심사 제출용`

**출시 노트 (683자)** — 심사에서 확인할 것을 먼저 답해 두는 구성이다. 기능 → 계산 기준 → 정책 순.

```
세후 실수령액 계산기 v1.0.0 첫 출시입니다.

[기능]
· 받고 싶은 세후 월급을 넣으면 그 돈을 받기 위한 연봉을 역산합니다. 이 앱의 핵심 기능입니다.
· 반대 방향(연봉 → 월 실수령)과 항목별 공제 내역(국민연금·건강보험·장기요양·고용보험·소득세·지방소득세)을 함께 보여 줍니다.
· 부가 기능으로 같은 연봉의 과거 연도 실수령 비교, 퇴직금, 미사용 연차수당 계산을 넣었습니다.

[계산 기준]
· 국세청 근로소득 간이세액표 2026-03-01 시행판과 2026년 4대 사회보험 요율·상하한을 적용했습니다.
· 화면마다 적용 기준일과 참고용 계산이라는 문구를 표시합니다. 연말정산 결과는 반영되지 않는다는 점도 함께 적었습니다.
· 데이터 출처와 확인일자는 설정 > 데이터 출처에 링크로 두었습니다. 국세청·공단이 제공하는 서비스로 오인될 문구는 쓰지 않았습니다.

[정책]
· 금융 상품을 소개하거나 연결하지 않고, 연봉이나 이직을 권하는 안내도 없습니다.
· 서버가 없습니다. 입력한 금액은 기기 안에서만 계산되며 외부로 전송되지 않습니다.
· 사용자 간 경쟁, 현금성 보상, 확률형 요소가 없습니다.
· 광고는 리워드 1개(과거 연도 비교·저장 비교 기능을 하루 동안 열 때만)와 스크롤 화면 하단 배너 1개입니다. 인트로·로딩·바텀시트에는 넣지 않았고, 리워드 보상은 시청을 끝냈을 때만 지급합니다.
```

```
세후 실수령액 계산기 v1.0.0 첫 출시입니다.

받고 싶은 세후 월급으로 필요한 연봉을 역산하는 것이 핵심 기능이고, 반대 방향 계산과 항목별 공제 내역, 퇴직금·연차수당 계산을 함께 제공합니다.

국세청 간이세액표 2026-03-01 시행판과 2026년 4대보험 요율을 적용했고, 화면마다 기준일과 참고용 계산 문구를 표시합니다. 서버가 없어 입력 금액은 기기 안에서만 계산됩니다. 금융 상품 연결, 경쟁·현금성 보상·확률형 요소는 없습니다. 광고는 리워드 1개와 스크롤 하단 배너 1개입니다.
```

→ 검토 요청 화면에서 출시 노트 입력.

## 2. 채널톡 사전 상담 메시지

계산기라 fx-replay보다 위험이 낮지만, 세액을 다루므로 카테고리와 자문 해당 여부는 미리 확인하는 편이 낫다.

> 안녕하세요. 비게임 미니앱 출시를 준비 중이며, 카테고리와 심사 기준을 미리 확인받고 싶어 문의드립니다.
>
> **서비스 개요**
> 국세청이 공개한 근로소득 간이세액표(소득세법 시행령 별표2)와 4대 사회보험 요율로 월급 실수령액을 계산하는 도구입니다. 특징은 방향입니다. 기존 계산기가 "연봉 → 실수령"만 계산하는 것과 달리, 이 앱은 **"받고 싶은 세후 월급 → 필요한 연봉"을 역으로 계산하는 것이 첫 화면**입니다. 퇴직금·연차수당 계산기도 함께 제공합니다.
>
> **등록 카테고리**: 생활 > 편의 > 도구 (비게임). 재테크 계열은 피했습니다
>
> **심사 기준을 고려해 다음과 같이 설계했습니다**
> 1. **금융 상품을 다루지 않습니다.** 대출·적금·보험·카드·증권 어떤 상품도 노출·추천·연결하지 않습니다. 이 연봉이면 대출 한도가 얼마인지 같은 파생 기능도 넣지 않았습니다.
> 2. **세무 자문이 아닙니다.** 모든 결과에 "간이세액표·공단 요율 기준 참고용 계산입니다. 실제 공제액은 회사·개인 상황에 따라 다를 수 있어요", "연말정산 결과는 반영되지 않습니다", 적용 기준일을 함께 표시합니다. 연봉을 얼마로 하라거나 이직을 권하는 표현은 빌드 단계에서 자동으로 차단하고 있습니다.
> 3. **개인정보를 수집하지 않습니다.** 서버가 없습니다. 입력한 금액은 기기 안에서만 계산되고 어디로도 전송되지 않습니다. 저장은 사용자가 명시적으로 누른 경우에만 하고 전체 삭제 기능을 제공합니다.
> 4. **경쟁·보상 요소가 없습니다.** 순위, 현금성 보상, 확률형 요소가 없습니다.
>
> **데이터 출처**
> - 근로소득 간이세액표: 국가법령정보센터 소득세법 시행령 별표2 (2026-03-01 시행판), 공공데이터포털 국세청 파일(이용허락범위 제한 없음)

> - 데이터는 앱 번들에 정적으로 포함되며 런타임에 외부 서버를 호출하지 않습니다.
> - 앱 내 결과 화면과 설정 > 데이터 출처 화면에 출처와 확인일을 표기했고, "국세청·공단이 제공·인증한 서비스가 아닙니다"를 함께 넣었습니다.
>
> **수익화 항목**
> - 인앱 광고만 사용합니다. 보상형(광고를 보면 당일 자정까지 시간축 비교·저장 계산 비교·저장 20개가 열립니다), 배너(홈·상세·저장 목록 하단).
> - 핵심 기능인 역산·정방향 계산과 공제 상세, 퇴직금, 연차수당은 광고 없이 무제한 무료입니다.
> - 인앱 결제와 자체 현금성 보상은 없습니다.
>
> **여쭙고 싶은 것**
> 1. 위 설계로 선택한 카테고리가 적절한지, 혹은 다른 카테고리를 권하시는지
> 2. 공개된 세액표로 세액을 계산해 보여 주는 것이 세무·금융 자문 관련 조항에 해당하는지
> 3. 광고 보상으로 "당일 자정까지 일부 기능 열기"를 주는 구조가 보상 정책에 맞는지
> 4. 매년 세액표·요율이 개정되면 데이터만 교체해 업데이트하게 되는데, 그때마다 심사가 필요한지
>
> 필요하시면 화면 흐름이나 문구 목록을 추가로 보내드리겠습니다. 감사합니다.

### 3-3. 남은 작업

**의존 순서가 있다.**

1. **정산 준비** — 사업자 정보·정산 정보 등록은 **완료**(2026-09-07). 사업자가 하나라 두 앱에 모두 적용된다.
   남은 것은 **팝빌 가입과 인증서 등록**이다. 광고 그룹 생성과는 독립적이라 병행할 수 있다.
   절차와 매월 승인 기한은 [docs/SETTLEMENT.md](../../docs/SETTLEMENT.md) 참고 —
   **역발행 미승인이 2회 이상이면 미니앱 운영이 중단될 수 있다.**
2. **광고 그룹 생성** — **완료**(2026-09-08, 2개 등록). **남은 것은 발급된 ID 두 개를 `.env` 에 넣는 것이다.**
   앱 정보(카테고리) 등록을 먼저 끝낸 뒤에 만든다.
   미디에이션(광고 네트워크)이 앱 정보의 카테고리에 맞춰 자동 설정되기 때문이다.
   콘솔 광고 그룹 관리에서 **앱마다 2개**(리워드·배너)를 만든다. 검토는 없고 생성 즉시 상세 화면에 광고 그룹 ID가 나온다. 단 구글 등록까지 최대 2시간이 걸려 그전에는 광고가 안 붙을 수 있다.

   | 광고 유형 | 그룹 이름(안) | 보상 이름 | 수량 |
   |---|---|---|---|
   | 리워드 | `netpay-rewarded-gate` | 오늘 하루 열기 | 1 |
   | 배너 | `netpay-banner-bottom` | — | — |

   발급된 ID를 `.env` 의 `VITE_AD_REWARDED_ID`·`VITE_AD_BANNER_ID` 에 넣는다.
   앱이 읽는 키는 이 두 개뿐이고(`src/main.tsx`), 비면 그 광고만 붙지 않는다.

   **실 ID를 문서에 적지 않는다.** `.env` 에만 둔다(`.gitignore` 대상).
   2026-09-08 발급된 두 개는 `.env` 의 주석에 단계 표시와 함께 기록해 뒀다.

   **단계마다 넣는 값이 다르다.** `check:config` 가 양방향으로 막는다.

   | 단계 | 값 | 가드 |
   |---|---|---|
   | `npm run deploy` (QR 테스트) | `ait-ad-test-rewarded-id` / `ait-ad-test-banner-id` | 실 ID가 있으면 **빌드 실패** — 개발 단계에 실 광고를 쓰면 정책 위반 |
   | `npm run deploy:release` (출시) | 콘솔 실 ID (`ait.v2.live.*`) | 테스트 ID거나 비면 **빌드 실패**. 번들 스캔도 `ait-ad-test-` 문자열을 막는다 |

   **주의**: kit 은 광고 그룹 ID의 기본값을 두지 않는다(번들에 테스트 ID 문자열이 남아
   심사 반려된 적이 있어서다). `.env` 가 비면 광고가 아예 붙지 않는다.
   QR 테스트에서 광고 노출을 확인하려면 `.env` 에 **테스트 ID**를 넣고 `npm run build` 로 만든다.
   출시는 실 ID로 `npm run build:release`. 번들 검사가 두 경우를 구분해 처리한다.
3. **고객문의 이메일 확정** → `.env` 의 `VITE_SUPPORT_EMAIL` 과 콘솔 등록값을 같게 맞춘다.
4. **로고 확정** — 현재는 원화 기호 초안이다. 그대로 갈지 결정한다.
5. **테스트 번들 배포** — `npm run deploy`. 배포 메모를 붙이려면 `npm run deploy -- -m "메모"`(1000자).
   심사용 출시 노트는 이 메모가 아니다(1-5 참고).
   **배포 API 키는 앱 범위다.** fx-replay 를 배포하는 `default` 키로 net-pay 를 올리면
   `4031 앱이 없거나 앱 정보에 접근할 수 있는 권한이 없어요` 가 난다(2026-09-08 실제로 겪었다).
   키는 **콘솔 → 워크스페이스 선택 → 왼쪽 메뉴 `키`** 에서 발급한다. 발급할 때 적용 범위를
   **전체 앱** 또는 **특정 앱**으로 고르는데, net-pay 만 고르면 그 키는 net-pay 전용이 된다.
   받은 키를 `npx ait token add net-pay` 로 프로필에 넣는다(대화형이라 쉘 히스토리에 안 남는다).
   `deploy` 스크립트가 `--profile net-pay` 로 그 키를 쓴다.
   `ait build` 는 `.ait` 아티팩트를 **로컬에 만들기만** 하고, 업로드는 `ait deploy` 가 한다.
   그래서 `npm run build` 만으로는 기기에서 열 수 없다.
   `ait build` 가 끝에 찍는 `deploymentId` 도 업로드 증거가 아니다 — 빌드가 로컬에서 만들어
   `.ait` 안 `bundle.json` 에 넣은 값이다.
6. **QR 테스트** — 배포된 번들을 실기기에서 확인한다(3-2). **이때 스크린샷을 함께 찍는다.**
7. **스크린샷 등록** — 앱 정보를 수정해 5장을 올린다(1-3 구성안).
   스크린샷은 선택 사항이지만 역산이라는 차별점을 첫 장에서 보여줄 수 있어 넣는 편이 낫다.
8. **출시 번들 배포** — `.env` 를 실 광고 ID로 바꾸고 `npm run deploy:release`.
   실 ID가 없거나 번들에 테스트 ID가 남아 있으면 막힌다.
9. **심사 제출** — 영업일 3일, 카테고리에 따라 7일 이상.
   **주의**: 새 번들을 올리면 그 번들로 테스트를 1회 이상 해야 검토 요청 버튼이 활성화된다.
   콘솔 배포 조회의 `isTested` 필드가 그 상태다(첫 배포 직후 `false`, `reviewStatus: CREATED`).
   실 ID로 올린 출시 번들도 QR 테스트를 한 번 거쳐야 한다.

**스크린샷과 앱 정보 등록의 의존 관계**

스크린샷을 등록하려면 실기기에 앱을 띄워야 하고, 띄우려면 번들을 배포해 QR 테스트를 해야 한다.
그래서 앱 정보는 **두 번에 걸쳐** 채운다.

```
앱 등록 + 기본 정보(스크린샷 제외)   ← 1차. 카테고리가 있어야 광고 그룹 미디에이션이 붙는다
        ↓
광고 그룹 생성 → .env 테스트 ID
        ↓
npm run deploy → QR 테스트 → 스크린샷 촬영
        ↓
앱 정보 수정해 스크린샷 등록          ← 2차
        ↓
npm run deploy:release → QR 테스트 1회 → 심사 요청
```
