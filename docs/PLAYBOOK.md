## 0. 원칙 (모든 앱에 공통)

1. **문서가 코드보다 먼저.** PROJECT_CONTEXT → PRD → 기능 명세 → 화면 흐름이 끝난 뒤 코드를 쓴다. 확정된 결정은 재논의하지 않는다. 확인 결과가 전제를 바꾸면 "재논의"가 아니라 "확인 결과가 전제를 바꿨다"로 근거와 함께 제시한다.
2. **차별점은 하나, 나머지는 표준 수준.** 첫 화면에서 설명 없이 체감되는 훅 하나 + 공유 카드에 쓸 요소 하나. 출시 속도가 우선이다.
3. **v1.0은 광고 전용, 서버 0.** 인앱결제는 토스 로그인 + mTLS 파트너 서버가 필요하므로 v1.1로 미룬다. 데이터는 전부 번들에 정적으로 넣고 런타임 외부 호출은 앱인토스 SDK(광고)만.
4. **비용 0원.** 데이터·인프라·입점 모두 무료. 정산에 필요한 사업자 등록과 팝빌만 예외.
5. **카테고리는 금융을 피한다.** 유틸리티나 라이프·콘텐츠. 재테크·금융은 금융 조항 렌즈로 심사된다. 게임·교육도 피한다(등급분류 비용, 자격 요건).
6. **포트폴리오.** 앱 하나의 광고 수익은 작다. 같은 템플릿으로 여러 개를 만들고 `intoss://` 스킴으로 서로 링크한다.
7. **화면 시안은 claude-design 으로 먼저.** 화면을 새로 만들거나 흐름을 바꿀 때는 `/design` 캔버스로 시안을 만들어 승인받고 구현한다(2-10). 색·간격만 고치는 건 예외.
8. **공용 코드는 `@ait/kit`.** 광고·저장·네비·백스택·공유·환경·i18n·익명 사용자는 앱 안에 다시 만들지 않는다. 설계는 [SHARED_PACKAGE.md](SHARED_PACKAGE.md).
9. **정확성은 원문으로 증명한다.** 계산 결과는 공공 계산기·법령 원문과 대조한 골든 테스트로 고정하고 `FACT_CHECK.md`에 기록한다. 기대값은 구현 코드를 거치지 않는 경로로 만든다.
10. **프로젝트 계획은 독립이다.** 각 앱의 착수·진행·출시 일정은 그 앱 안에서만 정한다. **다른 앱의 상태(심사 제출, 승인, 반려)를 착수 조건으로 걸지 않는다.** 세션이 병렬로 돌기 때문에 남의 앱 진행을 확인하려면 담당 범위를 벗어나야 하고, 그 앱이 지연되면 이유 없이 함께 멈춘다. 앱 사이에 진짜 의존이 있다면(공용 패키지 변경, 사업자 공통 항목) 그 대상만 콕 집어 적고, 없으면 "바로 착수"가 기본값이다.

## 2. 단계별 체크리스트

### 2-1. 아이디어 후보 비교
후보를 3~4개 뽑아 같은 축으로 비교한다. 가이드·안내형 앱은 만들지 않는다(독자가 개발자면 채널이 틀렸다).

| 축 | 통과 기준 |
|---|---|
| 대상 | 토스 일반 사용자(만 19세 이상)가 바로 쓰는 도구. 개발자·전문가 대상 아님 |
| 서버 | 0. 데이터가 불변이거나 갱신이 연 몇 회 이내 |
| 데이터 라이선스 | 상업 이용 가능(법령, 공공누리 1유형, 한국은행 작성 통계, "이용허락범위 제한 없음") |
| 기존 자산 재사용 | `@ait/kit` + 기존 파이프라인(ECOS, 법령 별표 파서, HWPX) 중 재사용 가능한 것 |
| 심사 리스크 | 금융 상품·투자 자문·법률 자문·의료·게임성에서 먼 것 |
| 수요 | 상시 수요 우선. 시즌성이 강하면 광고 수익이 불안정 |
| 차별점 | 한 줄로 말할 수 있는 훅 하나 |

- [ ] 비교표 작성 → 1개 선정, 나머지는 후속 후보로 기록
- [ ] 선정 이유 3줄

### 2-2. PROJECT_CONTEXT
기획 대화의 인계 문서. 구조: 한 줄 정의 / 확정된 핵심 결정(표) / 지켜야 할 제약(심사 정책) / 데이터 전략 / 수익 모델 / 인프라 / 제품 설계 포인트 / 확인 필요(체크박스) / 다음 단계 / 참고.
- [ ] 앱 이름(국문·영문·폴더명) 후보 — 영문 15자 이내 명사형
- [ ] 차별점(메인 훅)과 공유 카드 요소 확정
- [ ] 카테고리 결정과 이유
- [ ] 착수 시점 — 기본값은 **바로 착수**. 다른 앱의 심사·출시 상태를 조건으로 걸지 않는다(0장 9). 진짜 의존(공용 패키지 변경 등)만 대상을 콕 집어 적는다
- [ ] "확인 필요" 항목마다 누가(사용자 결정 / 조사) 닫는지 표시

### 2-3. 데이터·라이선스 검증
- [ ] 소스마다 작성기관·이용 조건·원문 URL·확인일. ECOS는 통계표별 `ORG_NAME` 확인(한국은행 작성만 출처표시로 상업 가능, 타 기관은 승인 필요)
- [ ] 공공데이터포털은 유형 확인(1유형 OK, 2유형 상업 금지). 법령·고시는 저작권 보호 대상 아님(저작권법 제7조)
- [ ] 자동 수집 가능 여부: 국가법령정보센터 **별표는 평문 다운로드 가능**(`lsBylTextDownLoad.do`), **조문 본문은 JS라 불가** → 상수 + 출처 URL. 공공데이터포털 HWPX는 ZIP+XML로 의존성 없이 파싱 가능. 홈택스·손택스·4대보험센터·법령 조문은 브라우저로만 조회
- [ ] 데이터 갱신 주기와 갱신 방법(데이터 교체 → `check:data` → 재제출)
- [ ] 심사 방어용 컷오프가 필요한지(fx-replay는 시세를 12개월 컷오프, 계산기류는 최신값 필수)

### 2-4. PRD
net-pay PRD의 12장 구조를 그대로 쓴다: 0 확정 사항 / 1 서비스 정의(한 줄, 무엇이 아닌가, 왜 이 조합, 타깃, 성공 지표) / 2 심사 대응 원칙 A~D(금융 상품 거리, 자문 아닌 참고, 개인정보 최소화, 광고 보상은 기능 해제만) + 콘솔 설명 문구 초안 / 3 핵심 흐름 / 4 기능 요구사항(CE·DT·UI·MZ·US, P0/P1/P2) / 5 데이터 소스 / 6 수익 / 7 아키텍처 / 8 리스크 매트릭스 / 9 범위 제외 / 10 마일스톤 / 11 열린 질문 / 12 변경 이력.
- [ ] 면책·기준일 문구 확정(B1·B2), 금지어 그룹 초안(B3)
- [ ] 게이트 구성: 메인 훅은 무료, 공유 카드는 무료(유입 수단), 게이트는 "결과를 본 직후 더 알고 싶은 것"
- [ ] 열린 질문을 사용자에게 번호로 묻고 전부 닫은 뒤 "확정"

### 2-5. 기능 명세
- [ ] 0장 상수·용어(값·출처), 1장 데이터 모델(TS 인터페이스), 2장 화면 목록·라우팅, 3장 기능별 동작 + AC, 4장 파이프라인, 5장 비기능, 6장 테스트 매트릭스, 7장 오픈 이슈
- [ ] 엔진은 순수 함수, AC는 손으로 검산한 숫자
- [ ] 저장소 스키마(`createStore('<접두어>')`), 이벤트 로그(금액은 어떤 형태로도 넣지 않음)
- [ ] 문구 린트 금지어 3그룹(상품·권고·기타)과 화이트리스트

### 2-6. 화면 흐름
- [ ] mermaid 네비 맵 + 뒤로가기 규칙(첫 화면 = 종료)
- [ ] 공통 레이아웃(자체 헤더 없음, 배너는 스크롤 마지막 요소, 잠금은 자리표시자)
- [ ] 화면별 저해상도 와이어프레임, 플로우 시퀀스, **카피 일람(키·문구)** — 이 표가 `ko.json`의 원본이 된다
- [ ] 디자인 토큰은 net-pay 6장 공유, 컴포넌트 인벤토리에 재사용 출처 표기

### 2-7. 워크스페이스 생성
- [ ] 루트 `package.json` `workspaces`에 폴더 추가, `npm install`은 루트에서
- [ ] `dev` 포트 배정(fx-replay 5173, net-pay 5174, rent-calc 5175, 다음은 5176)
- [ ] net-pay `package.json` scripts 복사: `check`(typecheck·lint:copy·test:run), `data:fetch`, `data:build`, `check:data`, `check:config`, `build`, `build:release`
- [ ] `apps-in-toss.config.ts`, `@apps-in-toss/web-framework` 3.3.x, Vite + React + TS, vitest
- [ ] `@ait/kit` import. 앱별 주입값: Storage 접두어, 광고 그룹 ID(`.env`), 금지어 사전, 앱 이름
- [ ] `.env`는 커밋 금지(루트 .gitignore). `VITE_SUPPORT_EMAIL`, `VITE_AD_REWARDED_ID`, `VITE_AD_BANNER_ID`
- [ ] 루트 README 표에 한 줄 추가

### 2-8. 데이터 파이프라인
- [ ] 원본을 `data-src/`에 보존, 변환 결과를 `src/data/*.json`에. `meta`에 source·url·fetchedAt·license
- [ ] 파서 단정(구간 연속성, 단조성, 행 수)
- [ ] `check:data`가 프로덕션 빌드를 게이트(기준일 신선도, 미확인 항목, 개발용 합성 데이터 플래그)
- [ ] 개발용 합성 데이터에는 `dev: true` 플래그 + 화면 배너, 프로덕션 빌드 차단

### 2-9. 엔진 + 골든 테스트
- [ ] 순수 함수 + 단위 테스트(AC 그대로)
- [ ] 골든 케이스 20건 내외. 기대값은 원문 숫자 리터럴 산술 또는 공공 계산기 브라우저 조회 결과. `FACT_CHECK.md`에 조회 조건·결과·조회일 표로
- [ ] 절사·반올림 규칙을 원문(고시·계산기)과 맞추고 테스트로 고정. 부동소수 오차 가드(1원 미만 = 0)
- [ ] 단조성 가정은 측정으로 확인(net-pay 실수령은 연봉에 단조가 아니었다)

### 2-10. 화면 시안 — 코드보다 먼저 (필수)

**화면을 새로 만들거나 구조를 바꿀 때는 `/design`(claude-design)으로 시안을 만들어 사용자 승인을 받은 뒤 구현한다.** CSS 부터 손대면 구조 문제가 보이지 않는다.

- [ ] `/design` 으로 아트보드를 만든다. 화면마다 하나, 컴포넌트 시트 하나. `canvas.json` 으로 배치
- [ ] 작업 파일은 `<app>/design/*.dc.html` 에 커밋한다. 다음 변경도 여기서 다시 씨딩한다
- [ ] **기존 토큰을 그대로 쓴다.** `src/styles.css` 의 값을 시안에 옮겨 적고, 새로 만드는 것만 새 값으로 한다
- [ ] 사용자 승인 뒤 구현. 승인 없이 코드로 넘어가지 않는다
- [ ] 구현 후 브라우저에서 375·390px 확인 → QR 테스트

**왜 필수인가** (net-pay, 2026-09-08): 실기기 테스트에서 "디자인이 엉망"이라는 지적을 받고 CSS 를 두 번 고쳤지만 두 번 다 반려됐다. 문제는 색·간격이 아니라 **구조**였다 — 한 화면에 입력과 결과를 다 얹고, 화면 전환이 없고, 하단 네비게이션이 없었다. 시안을 먼저 만들자 한 번에 통과했다. 토큰만 고치는 수준은 시안이 필요 없지만, 화면이 늘거나 흐름이 바뀌면 반드시 시안부터다.

**한계는 정직하게**: 시안은 시안이고 구현은 코드다. 시안이 예뻐도 실기기에서 다를 수 있어 QR 테스트는 그대로 필요하다(폰트·세이프 에어리어·키패드).

## 4. 저장소·세션 규칙

### 4-1. 세션 범위
여러 Claude 세션이 같은 저장소에서 다른 앱을 동시에 작업한다. 세션마다 **담당 앱 하나**를 정하고 아래 경로만 만진다.

| 구분 | 경로 | 할 수 있는 것 |
|---|---|---|
| 담당 앱 | `<app>/` | 수정·커밋 |
| 공용 패키지 | `packages/ait-kit/` | 수정·커밋. 바꾸면 모든 앱 `npm run check` 통과 확인 |
| 공통 문서 | `docs/`, `CLAUDE.md`, `README.md` | 수정·커밋 |
| 다른 앱 | `<other-app>/` | **읽기만.** 참고 코드는 담당 앱으로 가져와 쓰고 원본은 고치지 않는다 |

**계획도 범위 안에서만 세운다(0장 9).** 담당 앱의 일정만 관리하고, 다른 앱의 심사·출시 상태를 확인하거나 그 절차를 안내하지 않는다. 사용자가 다른 앱의 진행을 물으면 담당 세션을 안내한다. 담당 앱 문서에 "다른 앱 제출 후 착수" 같은 조건이 남아 있으면 사용자에게 알리고 지운다.

- 공용 패키지 변경이 다른 앱 코드 수정을 요구하면 직접 고치지 않고 사용자에게 알린다. 그 앱의 세션이 처리한다.
- 다른 앱의 미커밋 변경이 `git status`에 보이면 보고만 한다.

### 4-1-1. 세션의 컨텍스트는 스냅샷이다
같은 작업 트리를 여러 세션이 동시에 고친다. 파일을 읽은 순간 이후의 변경은 보이지 않는다. 실제로 겪은 두 가지:

- 공용 문서에 표를 만들어 보고한 직후 다른 세션이 그 표에 열을 추가했다. 보고한 내용이 그 시점에 이미 낡아 있었다.
- 다른 앱의 `.env` 에 실 광고 ID가 있는 것을 보고 "빌드 가드에 막힌다" 고 지적했는데, **그 앱은 이미 출시·심사 단계라 실 ID가 정상**이었다. 담당 앱의 단계를 남의 앱에 투사한 것이다.

그래서 세 가지를 지킨다.
1. **첫 작업 전에 루트에서 `npm run status`.** 앱별 단계·광고 ID 단계·가드 채택·마지막 커밋을 파일에서 파생해 보여준다. 남의 앱 상태를 추측하지 않는다.
2. **공용 문서(`docs/`, `CLAUDE.md`, `README.md`)는 쓰기 직전에 다시 읽는다.** 낡은 컨텍스트로 덮어쓰면 다른 세션의 편집이 사라진다.
3. **다른 앱을 언급하기 전에 `git log -1 -- <app>` 으로 그 앱의 최근 작업을 확인한다.** 파일 내용만 보고 단계를 판단하지 않는다.

**상태는 손으로 적지 않는다.** 파일에서 읽어낼 수 있는 것은 `npm run status` 가 파생한다. 파생할 수 없는 것(콘솔 등록·심사 제출·반려 사유·정산)만 `<앱>/STATUS.md` 에 적는다. 그 파일은 담당 세션만 고치니 세션 간 충돌이 없다.

### 4-2. 커밋 규칙
- **커밋 범위 = 세션 범위.** 경로를 지정해 스테이징한다. `git add -A`, `git add .`, `git commit -a` 금지.
  ```bash
  git add <app> packages/ait-kit docs CLAUDE.md README.md
  git commit -m "<type>(<app>): <요약>"
  ```
- 커밋 메시지 접두어: `feat(<app>)`, `fix(<app>)`, `docs(<app>)`, `docs` (공통 문서), `chore(kit)` (공용 패키지).
- 커밋 전 `git status`에서 스테이징된 파일이 전부 세션 범위 안인지 확인한다.
- `.env`(ECOS 인증키, 광고 ID) 절대 커밋 금지. `*.ait`, `dist`, `.claude/`는 gitignore.

### 4-3. 그 밖에
- 루트가 git 루트, npm workspaces 모노레포(비공개 `eungbin/app-in-toss`). `npm install`은 루트에서.
- 문서는 앱 폴더 `docs/` 아래, 공통 문서만 루트 `docs/`.

## 6. 배운 것 (함정 목록 — 새 앱마다 추가)

- **ECOS는 통계표별 작성기관을 봐야 한다.** 한국은행 작성만 출처표시로 상업 가능. KOSPI는 한국거래소, 원자재는 IMF(비상업 한정), 해외지수는 OECD. 일별 통계표는 7개뿐이고 분봉 없음. (fx-replay)
- **인앱결제는 서버를 부른다.** 비소모품 복원에 토스 로그인 + mTLS 상태 조회 API. 그래서 v1.0 광고 → v1.1 결제로 분할. (fx-replay)
- **자체 헤더·뒤로가기 버튼은 체크리스트 위반.** 토스가 네비 바를 그린다. (fx-replay)
- **공공데이터포털 파일은 최신 개정판이 아닐 수 있다.** 국세청 간이세액표는 포털이 2024판, 최신은 홈택스·국가법령정보센터 별표. (net-pay)
- **법령 별표는 평문으로 자동 수집되고 조문은 안 된다.** `lsBylTextDownLoad.do` POST(bylSeq, title, mode=0). 조문 화면·홈택스·손택스·4대보험센터는 JS 앱. (net-pay, rent-calc)
- **계산 결과가 단조라고 가정하지 말 것.** 실수령은 연봉에 단조가 아니었다(표 상한 구간에서 낙폭). 역산은 격자 탐색 + 목표 달성 재확인. (net-pay)
- **절사·반올림은 원문 계산기와 맞춰야 한다.** 고용노동부는 1일 평균임금 소수를 유지한다. floor 하나로 66원이 틀렸다. (net-pay)
- **출시 번들에 테스트용 광고 그룹 ID 문자열이 남으면 반려된다.** kit이 테스트 ID를 모듈 최상위에서 참조해 트리셰이킹이 되지 않았다. 런타임에 실 ID로 덮어써도 심사는 번들 문자열을 본다. 설정 검사로는 못 잡으니 빌드 산출물을 직접 스캔한다. (fx-replay)
- **정산은 팝빌이 필수고 인증서 종류가 제한된다.** 은행 금융거래용은 불가, 전자세금계산서용은 가능. 매월 4영업일 마감, 2회 미승인 시 운영 중단. (공통)
- **가이드·안내형 앱은 만들지 않는다.** 독자가 개발자면 토스 안이 아니라 GitHub·블로그가 채널이다. (rent-calc 기획)
- **법정 상한은 적용 범위를 먼저 나눠야 한다.** 주임법 5%·전환율 상한은 갱신·존속 중에만, 신규 계약엔 없다. 첫 화면에서 모드를 고르게 하지 않으면 잘못된 판정을 내보낸다. (rent-calc)
- **병행 세션의 `git add -A`가 내 파일을 쓸어 담는다.** rent-calc 문서 5개가 net-pay 커밋 두 개에 섞여 들어갔다. 세션 범위와 커밋 범위를 같은 경로 목록으로 고정한다(4장). (공통)
- **콘솔 비게임 카테고리 목록** (2026-09-08 콘솔 확인. 개발자 문서에는 없다)
  - 대분류: **생활** 하나뿐. 고를 게 없다.
  - 중분류 15개: 음식 · 교육 · 건강 · 교통 · 공공 · 소셜 · 편의 · 쇼핑 · AI · 비즈니스 · 콘텐츠 · 여행 · 일상 · 정보 · 재테크
  - 중분류는 복수 선택. 같은 중분류를 두 번 고를 수는 없다. 소분류는 일부 중분류에만 있고 **중분류마다 항목이 달라 목록화하지 않는다** — 콘솔에서 보고 고른다.
  - **계산기·도구류는 `편의` > 소분류 `도구`** 가 맞다(net-pay 실제 선택). 둘째 중분류가 필요하면 `정보`. `재테크` 는 금융 조항 렌즈로 검토될 여지가 커서 피한다(원칙 0장).
- **콘솔 카테고리는 비게임이 3단(대·중·소)이고 중분류를 복수로 고른다.** 문서 템플릿에 "카테고리: 유틸리티" 한 줄로 적어 두면 콘솔에서 막힌다. **대분류는 '생활' 하나뿐이라 고를 게 없고 실제 결정은 중분류에서 난다.** 같은 중분류를 두 번 고를 수는 없고, 소분류는 일부 중분류에만 있다. **중분류·소분류 목록은 개발자 문서에 없고 콘솔 UI에서만 볼 수 있다** — 그래서 문서에는 값을 못 박지 말고 선택 기준을 적고, 등록 후 실제 값을 기입한다. (net-pay)
- **디자인은 CSS 가 아니라 구조에서 먼저 틀어진다.** net-pay 는 토큰·간격을 두 번 고치고도 "올드하고 정적"이라는 지적을 받았다. 실제 원인은 한 화면에 입력과 결과를 다 얹은 것, 화면 전환이 없는 것, 하단 네비게이션이 없는 것이었다. `/design` 시안을 먼저 만들면 이게 보인다(2-10).
- **하단 탭은 미니앱이 직접 만든다.** 상단 바만 토스가 그린다. fx-replay 의 떠 있는 알약(`blur(20px) saturate(180%)`, 활성 `rgba(49,130,246,.10)`)을 세 앱이 공유한다. 하단 위치는 SDK 세이프 에어리어 기준 — CSS `env()` 금지.
- **kit 이 코드로 강제할 수 없는 항목은 [SHARED_PACKAGE.md](SHARED_PACKAGE.md) 6장 표로 전달한다.** `package.json` 스크립트·앱 금지 목록·화면 CSS 는 앱 소유라 kit 이 대신 넣어 줄 수 없다. 다른 앱에 반영이 필요하면 그 표에 적고 담당 세션이 처리한다.
- **앱 검색 키워드는 10개를 상한으로 잡는다.** 개발자 문서에 개수가 없다. 우선순위를 매기고 대기 후보를 따로 적어 둔다. 앱이 계산·제공하지 않는 값(예: 최저임금)은 관련 없는 키워드로 검수에서 걸릴 수 있어 넣지 않는다. (net-pay)
- **`ait build` 는 업로드하지 않는다.** `.ait` 아티팩트를 로컬에 만들기만 하고 업로드는 `ait deploy` 가 한다. build 만 돌리고 기기에서 안 열린다고 헤매게 된다. package.json 에 `deploy` / `deploy:release` 스크립트를 둔다. (net-pay)
  - **`ait build` 가 끝에 찍는 `deploymentId` 는 업로드 증거가 아니다.** 빌드가 로컬에서 만들어 `.ait` 안 `bundle.json` 에 넣은 값이다(직접 열어 확인). 이걸 보고 올라갔다고 착각하기 쉽다.
  - `-m` 은 **배포 메모**다(**120자**, `npm run deploy -- -m "메모"`). CLI 도움말은 1000자라고 하지만
    서버가 `메모는 120자 이하만 가능해요 (Code: -1)` 로 거절한다 — 도움말을 믿지 말 것. (photo-standard 2026-09-09) 심사 담당자가 읽는 **출시 노트(`releaseNote`)는 다른 필드**이고 콘솔 검토 요청 화면에서만 넣는다 — 배포 조회에 `memo` 와 `releaseNote` 가 따로 나온다. CLI 로는 출시 노트를 넣을 수 없다.
  - `.ait` 는 `.gitignore` 에 `*.ait` 로 빠져 있어야 한다.
- **배포 API 키는 콘솔 → 워크스페이스 선택 → 왼쪽 메뉴 `키` 에서 발급한다.** 발급할 때 적용 범위를 **전체 앱** 또는 **특정 앱**으로 고른다(개발자센터 확인, 2026-09-08). 토스페이먼츠 키(`test_sk`·`test_ck`)와 다른 것이다. 콘솔에 `.ait` 를 손으로 올리는 길도 있어서 CLI 가 막혀도 배포 자체는 가능하다.
- **`ImageResponse.dataUri` 는 데이터 URI 가 아니다.** `Device.getPhotos` / `openCamera` 가 `base64: true` 로 돌려주는 값은
  `data:image/jpeg;base64,` 헤더가 없는 **순수 base64 페이로드**다(안드로이드 실기기 확인, `/9j/4AAQSkZJ…`).
  이름을 믿고 `img.src` 에 그대로 넣으면 상대 경로로 해석돼 앨범·카메라가 **둘 다** 실패한다.
  `dataUriMime()` 도 빈 문자열을 돌려주므로 **형식 판정까지 조용히 어긋난다**. 받는 즉시 헤더를 붙여 정규화한다.
  브라우저에는 SDK 가 없어 이 차이가 드러나지 않는다 — 실기기에서만 터진다. (photo-standard 2026-09-09)
- **실기기 전용 실패는 원인을 화면에 띄우는 진단 빌드로 좁힌다.** 오류 문구를 "열 수 없어요" 하나로 뭉치면
  SDK 호출 실패·디코딩 실패·형식 문제가 구분되지 않아 QR 왕복만 늘어난다. `VITE_DIAG` 로 켜고
  `check:config --release` 와 번들 스캔이 출시 빌드에서 막는다. (photo-standard 2026-09-09)
- **배포 API 키는 앱 범위다.** 다른 앱을 배포하던 키로 새 앱을 올리면 `4031 앱이 없거나 앱 정보에 접근할 수 있는 권한이 없어요` 가 난다. 앱 이름으로 프로필을 만들고(`npx ait token add <앱>` — 대화형으로 물어 키가 쉘 히스토리에 남지 않는다) `ait deploy --profile <앱>` 로 고정한다. 키 문제인지 앱 이름 문제인지는 **같은 키로 다른 앱을 읽어 보면** 갈린다.
  ```
  GET .../api-public/v3/openapi/bundles/<앱>/deployments/<deploymentId>
  ```
  200 이 나오는 앱이 그 키의 범위다. 업로드 경로가 `bundles/<appName>/...` 이라 `apps-in-toss.config.ts` 의 `appName` 은 콘솔에 등록한 앱 식별자와 **정확히** 같아야 한다. (net-pay)
- **스크린샷 때문에 앱 정보를 두 번에 걸쳐 채운다.** 스크린샷을 등록하려면 실기기에 띄워야 하고, 띄우려면 번들을 배포해 QR 테스트를 해야 한다. 그래서 1차로 기본 정보(카테고리 포함 — 광고 그룹 미디에이션의 전제)를 넣고, QR 테스트 때 촬영해 2차로 스크린샷을 올린다. 새 번들은 그 번들로 테스트 1회를 해야 검토 요청 버튼이 열린다. (net-pay)
- **앱 검색 키워드도 SUBMISSION 에 미리 정해 둔다.** 토스 전체메뉴 돋보기 검색에 쓰인다. **앱 이름은 기본 포함**이라 이름을 키워드로 넣으면 칸 낭비고, **미니앱과 관련 없는 키워드는 검수에서 걸린다.** 개수·글자 수 제한은 개발자 문서에 없어 콘솔에서 확인해야 한다. 경쟁 서비스 이름은 오인 유도로 반려 사유가 될 수 있다. 검색량 많을 것 같은 순서로 적어 두고 칸이 모자라면 위에서 자른다. (net-pay)
- **기기 스크린샷은 콘솔 규격과 비율이 다르다.** 안드로이드 실기기 648×1390 vs 콘솔 세로 636×1048. 세로를 잘라 맞추면 표·탭바가 잘리니 **양옆에 흰 여백을 넣어 비율만 맞춘다**. 아래는 **탭바 알약 바로 밑**에서 끊는다 — 그보다 아래를 남기면 탭바 뒤로 반쯤 걸린 본문 한 줄이 들어가 렌더링 오류처럼 보인다. 상태바·내비 바는 잘라낸다. 자세한 절차는 net-pay SUBMISSION 1-3. (net-pay)
- **콘솔 규격 숫자는 문서에 박아 둔다.** 로고 정사각형 600×600 PNG **투명 배경 불가**, 스크린샷 세로 636×1048·가로 1504×741(**선택 사항**), 앱 이름 영문은 15자 이내 발음하기 쉬운 명사형. 매번 다시 찾게 된다. (net-pay)
- **사전 상담은 선택이지만 채널톡 설명은 준비해 둔다.** 네 앱 모두 사전 상담 없이 출시·제출했다. 다만 **앱 정보 검토에서 "앱 정보만으로는 서비스 확인 및 심사가 어렵다. 채널톡으로 핵심 기능·이용 방식을 전달해 달라"는 반려**가 올 수 있다(rent-calc, 2026-09-09). 그때 바로 보낼 문구를 SUBMISSION에 두면 왕복 한 번을 줄인다. (rent-calc)
- **상세 설명이 "무엇이 아니다"로 채워지면 반려된다.** rent-calc 첫 판(426자)은 판정 대상과 면책만 적고 이용 방식이 없어 반려됐다. 승인받은 net-pay(475자)·photo-standard(492자)는 둘 다 접속 → 행동 → 결과 흐름이다. **승인된 앱의 상세 설명을 먼저 읽고 같은 골격으로 쓴다.** (rent-calc)
- **비게임 카테고리는 대분류가 '생활' 하나다.** 중분류 15개(음식·교육·건강·교통·공공·소셜·편의·쇼핑·AI·비즈니스·콘텐츠·여행·일상·정보·재테크)에서 실제 결정이 나고 복수 선택이다. 소분류는 콘솔에서만 보인다. 계산기·도구는 **편의**, 자료 조회 성격이면 **정보**. **재테크는 피한다**(금융 조항 렌즈). 공공기관 자료를 쓰더라도 **공공은 피한다** — "○○가 제공·인증한 서비스가 아닙니다"를 넣는 앱이 공공 카테고리에 있으면 모순이다. (net-pay, rent-calc)
- **출처 표기를 사용자 입력값에 그대로 붙이면 안 된다.** 기준금리를 사용자가 직접 넣을 수 있게 했더니 결과 하단에 "기준금리 8.5% (2026-09-05 한국은행 공시)"가 나와 입력값이 공시값처럼 보였다. 문구를 갈라 "(직접 입력)"으로 바꿨다. (rent-calc)
- **공공 계산기의 반올림값을 그대로 입력해도 판정이 뒤집히지 않게 가드를 둔다.** 계산기가 알려 준 법정 최대 월세(229,167원 = 229,166.67 반올림)를 넣으면 내부 환산값이 상한을 80원 넘어 "초과"가 됐다. 표시 해상도(1원)보다 작은 차이는 판정하지 않는다. (rent-calc)
- **착수 조건을 다른 앱에 걸지 말 것.** rent-calc를 "net-pay 심사 제출 이후 착수"로 잡았더니, 담당 세션이 남의 앱 제출 상태를 계속 확인하고 그 절차까지 안내하는 범위 이탈이 생겼다. 1인 개발이라 시간이 하나라는 전제로 만든 조건인데 세션이 병렬로 돌면서 전제가 깨졌다. (rent-calc)
