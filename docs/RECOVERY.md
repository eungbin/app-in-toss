# 소스 유실 앱 복구 절차

| 항목 | 내용 |
|---|---|
| 문서 버전 | v0.1 (2026-09-09) |
| 용도 | **콘솔에 출시돼 있는데 소스가 없는 앱**을 되살릴 때 따르는 순서 |
| 근거 | `photo-standard`("사진규격") 복구 — 2026-09-09 심사 승인·출시, 반려 없음 |
| 신규 앱은 | 이 문서가 아니라 [PLAYBOOK.md](PLAYBOOK.md) |

신규 개발과 다른 점만 적는다. 문서·엔진·시안·구현·출시의 큰 순서는 PLAYBOOK 그대로다.

---

## 0. 복구가 신규와 다른 세 가지

1. **출발점이 백지가 아니다.** 콘솔에 이름·부제·카테고리·키워드·딥링크가 이미 있다. 그 값이 곧 요구사항이다.
2. **바꾸지 않는 것이 기본이다.** 등록값을 건드리면 심사 범위가 넓어진다.
3. **복구는 곧 재심사다.** 새 번들은 검토 요청 → 승인 → 출시를 다시 거친다(비게임 최대 3영업일).

---

## 1. 정말 소스가 없는지 먼저 확인한다

찾을 곳을 다 뒤진 뒤에 재구현을 결정한다. 순서대로 30분이면 끝난다.

```bash
find ~ -maxdepth 4 -iname "*<앱이름>*" -not -path "*/Library/*" 2>/dev/null
gh repo list --limit 200 --json name,updatedAt --template '{{range .}}{{.name}}\t{{.updatedAt}}{{"\n"}}{{end}}'
git log --all --diff-filter=D --name-only --oneline    # 삭제된 경로
```

**앱인토스에서는 소스를 되받을 수 없다.** `.ait` 번들(빌드 산출물)만 보관하고 콘솔 UI에 내려받기가 없다.
`ait` CLI 의 배포 API 도 `upload-start` / `upload-complete` / `deployments/<id>` 조회 셋뿐이다.
따라서 위에서 안 나오면 **재구현이 유일한 길이다.**

---

## 2. 콘솔에서 회수한다 — 이것이 요구사항이다

### 2-1. 조회 API (배포 키가 있으면 CLI 없이 바로)

```bash
KEY=$(python3 -c "import json,os;print(json.load(open(os.path.expanduser('~/.ait/credentials')))['<프로필>'])")
curl -s -H "Authorization: Bearer $KEY" \
  "https://apps-in-toss.toss.im/console/api-public/v3/openapi/bundles/<appName>/deployments/<deploymentId>" \
  | python3 -m json.tool
```

`deploymentId` 는 콘솔 → 앱 출시 → 버전 목록에서 번들 버전을 누르면 툴팁으로 나온다.

돌려주는 것: `miniAppId` · `appName` · `versionName` · `sdkVersion` · `reviewStatus` · `isTested` ·
`deployed` · `memo` · `releaseNote` · `isSdk3Deployed`.

**200 이 나오면 그 키가 그 앱 범위다.** 배포 키는 앱 범위라 다른 앱 키로는 `4031` 이 난다.
키를 앱 이름 프로필로 고정해 두면 섞이지 않는다.

```bash
npx ait token add <앱>        # 대화형 — 키가 쉘 히스토리에 남지 않는다
```

### 2-2. 콘솔 화면에서만 볼 수 있는 것

| 화면 | 회수할 것 |
|---|---|
| 앱 정보 | 부제, 카테고리(대·중·소), 검색 키워드, 고객문의 이메일, 로고, 스크린샷 유무 |
| 앱 출시 | 버전 목록, SDK 버전, 심사 상태, 배포 ID |
| 주요 기능 | 국문·영문 기능명, **딥링크 경로** — 진입점이 몇 개인지가 화면 설계를 좌우한다 |
| 홈 대시보드 | DAU·리텐션·유입. **구판이 왜 안 됐는지**를 말해 준다 |
| 인앱 광고 | 광고 그룹이 있는지. 없으면 수익이 0이었다는 뜻이다 |

photo-standard 는 여기서 **광고 그룹이 아예 없다**는 것을 발견했다. 출시해 놓고 수익화를 안 붙인
상태였고, 유저 4명·리텐션 0% 의 실제 원인이었다. 복구판에서 가장 먼저 고칠 항목이 그것이었다.

### 2-3. 지표를 읽을 때

낮은 리텐션이 곧 나쁜 앱은 아니다. **1회성 도구는 재방문이 원래 낮다.**
photo-standard 는 재방문을 KPI 에서 뺐다. 되풀이하지 말아야 할 것과 앱의 성격을 구분한다.

---

## 3. 바꾸지 않는다

| 항목 | 이유 |
|---|---|
| `appName` | 업로드 경로가 `bundles/<appName>/` 이다. 한 글자만 달라도 **다른 앱**을 찾는다 |
| 앱 이름·부제·카테고리·키워드 | 바꾸면 심사 범위가 넓어진다. 유저 인지도가 있으면 더더욱 |
| 고객문의 이메일 | `.env` 의 `VITE_SUPPORT_EMAIL` 과 콘솔 등록값을 같게 맞춘다 |
| 딥링크 | 진입점을 늘리려면 콘솔 주요 기능도 함께 고쳐야 한다 |

로고는 예외다. 구판 유저가 적으면 잃을 인지도가 없으니 교체를 검토할 만하다.

---

## 4. 되돌릴 수 없는 것

- **SDK 3.x 번들을 출시하면 2.x 로 롤백할 수 없다**(개발자 문서 명시). 구판이 2.x 면 편도다.
  다만 소스가 없어 돌아갈 대상 자체가 없으므로 실질 손해는 없다.
- **QR 테스트를 반드시 통과한 뒤 출시한다.** 출시는 사용자에게 즉시 반영된다.

---

## 5. 복구건에서 특히 조심할 것

photo-standard 에서 **실제로 터진 것들**이다. 셋 다 브라우저 검증으로는 드러나지 않았다.

### 5-1. 실기기에서만 터지는 SDK 차이
`ImageResponse.dataUri` 는 이름과 달리 **헤더 없는 순수 base64** 였다. 이름을 믿고 `img.src` 에 넣어
앨범·카메라가 **둘 다** 죽었고, `dataUriMime()` 이 빈 문자열을 돌려줘 **형식 판정까지 조용히 어긋났다.**
→ SDK 가 주는 값은 **이름이 아니라 실물로 확인한다.** 자세한 것은 [PLAYBOOK 6장](PLAYBOOK.md).

### 5-2. 오류 문구를 하나로 뭉치지 않는다
"열 수 없어요" 하나로는 SDK 호출 실패·디코딩 실패·형식 문제가 구분되지 않아 QR 왕복만 늘어난다.
**진단 빌드**를 만들어 원인을 화면에 띄운다.

```
.env            VITE_DIAG=1
check:config    --release 에서 켜져 있으면 빌드 실패
check:bundle    --release 에서 진단 문구를 찾아 실패
```

가드 두 겹을 먼저 걸고 진단을 넣는다. 트리셰이킹을 믿지 않고 **산출물을 직접 검색**해 확인한다.

### 5-3. 스크린샷은 검수 도구다
photo-standard 의 결과 화면 형식 오표기(`'any'` 프리셋이 JPEG 로 나가는데 "PNG" 표시)를
**스크린샷을 검수하다 발견**했다. 안 찍어 봤으면 그대로 출시됐다.
촬영본을 받으면 전처리 전에 **화면에 찍힌 값이 맞는지부터 읽는다.**

## 6. 스크린샷 (콘솔 규격 636 × 1048 PNG)

- **첫 장은 차별점**이다. 기능 목록이 아니라 "이 앱이 남과 다른 지점"을 보여 준다.
- 사람 얼굴을 쓰지 않는다. **도형으로 만든 실루엣**이면 초상권·개인정보 질의가 안 생긴다.
- **타사 로고·브랜드가 들어간 이미지를 원본으로 쓰지 않는다.** 남의 상표가 스토어에 실린다.
- 개발 전용 UI 가 보이면 안 된다. **출시 빌드에서 촬영한다.**

전처리 (안드로이드 648 × 1390 → 636 × 1048):

1. 위 44px 잘라내기 — 상태바 (토스 네비게이션 바는 남긴다)
2. 아래를 **걸쳐 있는 요소 위에서** 끊는다. 반쯤 잘린 버튼·글자는 렌더링 오류처럼 보인다
3. 세로는 그대로 두고 **좌우로만 넓혀** 비율을 맞춘다 (세로를 자르면 내용이 잘린다)
4. 여백은 단색이 아니라 **각 행의 가장자리 색을 늘려** 채운다 — 배경이 어두운 화면에 흰 띠가 생기지 않는다
5. LANCZOS 로 리사이즈, PNG 저장

구현은 photo-standard 복구 때 쓴 방식 그대로다. [photo-standard/docs/SUBMISSION.md](../photo-standard/docs/SUBMISSION.md) 1-3 참고.

---

## 7. 출시까지

1. 광고 그룹 발급 (리워드·배너) → `.env` 에 실 ID. **실 ID 는 커밋하지 않는다**
2. `npm run build` (테스트 ID) → QR 테스트
3. `npm run build:release` (실 ID) → 배포 → **그 번들로 QR 테스트 1회** (`isTested` 가 서야 검토 요청이 열린다)
4. 스크린샷 등록
5. 검토 요청 — **출시 노트는 콘솔 그 화면에서만 넣는다.** `ait deploy -m` 은 `memo`(120자)를 채운다
6. 승인 → 출시 버튼

실 광고 ID 번들로 QR 테스트할 때 **리워드를 끝까지 시청하지 않는다.** 자기 광고에 자기 노출을 만든다.

## 8. 남은 복구 대상

| 앱 | 상태 |
|---|---|
| `근무수첩` | **복구 완료.** appName `work-journal`, 2026-09-10 출시. 경위는 [../work-journal/STATUS.md](../work-journal/STATUS.md) |
| `Night:3D` | 게임. **삭제 대상**(2026-09-08 사용자 지시). 복구하지 않는다 |

**남은 복구 대상은 없다.** 아래 절차는 다음에 같은 일이 생길 때를 위한 것이다.

### 복구 세션이 첫 턴에 할 일

1. 루트에서 `npm run status` — 저장소 상태를 파일에서 파생한다
2. 이 문서 1장으로 **소스 유무 확인**
3. 2장으로 **콘솔에서 회수** — 조회 API + 화면 다섯 곳
4. 회수한 값으로 `<앱>/STATUS.md` 를 먼저 만든다. 콘솔 사실은 파일에서 파생할 수 없다
5. 그다음 PLAYBOOK 문서 단계

**앱 이름이 한국어면 폴더명·`appName` 은 콘솔 등록값을 그대로 확인한다.** 영문 케밥케이스일
것이고(`photo-standard`, `work-journal`) 추측하지 말고 콘솔에서 읽는다.

## 9. 근무수첩에서 새로 배운 것 (2026-09-10)

**"콘솔에 있다"가 "출시돼 있다"는 뜻은 아니다.** photo-standard 는 출시된 앱의 재제출이었지만
근무수첩은 **앱 정보만 승인되고 번들은 한 번도 출시된 적이 없었다**(번들 2개가 "검토 필요"에서
멈춰 있었다). 확인 순서를 바꿔야 한다 — 2장의 조회 API 에서 `deployed` 와 `isSdk3Deployed` 를
먼저 본다. 둘 다 false 면 지킬 유저 인지도가 없고, 로고·화면을 자유롭게 바꿀 수 있다.

**구판 화면은 사용자에게 부탁해 받는다.** 소스가 없어도 콘솔에 QR 테스트 번들이 남아 있으면
사용자가 실기기에서 열어 촬영할 수 있다. 근무수첩은 그렇게 11장을 받아 홈 1화면 + 시트 3종
구조와 근무지 폼 15개 필드를 복원했다. **상세 설명 한 문단보다 스크린샷 한 장이 정확하다.**
받은 것은 `<앱>/design/legacy/` 에 커밋하고 `docs/LEGACY_SCREENS.md` 로 정리한다.

**구판의 계산값을 골든으로 삼지 않는다.** 근무수첩 구판 화면의 4대보험 공제액(27,650원)은
건강보험 보수월액보험료 하한을 적용하지 않은 값이었다. 이미 원문 대조를 통과한 net-pay 엔진
값(32,355원)을 따랐다. 구판 화면은 **구조를 확인하는 근거**이고 수치의 근거는 원문이다.

**앱 정보 심사와 번들 심사는 별개다.** 스크린샷·부제·카테고리를 고치면 앱 정보 검토가 열리고,
번들은 버전 목록에서 따로 [검토 요청] 을 눌러야 한다. 앱 정보가 승인돼도 출시가 되지 않는다.
